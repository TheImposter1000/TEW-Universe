# TEW Universe Studio

Independent Windows desktop editor for **existing** Total Extreme Wrestling IX scenario records.

## Verified numeric code labels

The centralized `TewCodeLabels` catalog translates **346 verified numeric codes** in thirteen categories, based on mappings supplied by the TEW Universe maintainer. The worker categories are `tblWorker.Gender` (8), `Sexuality` (5), `Pronouns` (5), `Race` (9), `Based_In` (65), `Nationality` (200), `Style` (16), `CompetesAgainst` (5), and `Outsiderel` (4). Tag teams translate `tblTeam.Type` (6). Relationships translate `tblRelation.P_Rel` (9), `R_Rel` (7), and `F_Rel` (7), each beginning at code 0. Some examples: Gender 5 is Female; Sexuality 5 is Pansexual; Pronouns 3 is They-Them; Race 7 is South Asian; Based In 22 is Manitoba; Nationality 36 is Canadian; Style 13 is Technician Flyer; Competes Against 5 is Primary Women's Division; Outside Relationship 1 is No; Tag Team Type 4 is Inactive Permanent Unit. These mappings are **application labels only** and never change the TEW IX database schema.

Known values appear as readable names in worker profile fields, worker header and Quick Facts, gender/nationality/region roster filters, plus existing-tag-team and new-tag-team type selections. Editors still keep and save the corresponding **original numeric code**, and filters still match the original stored values. Any unknown/unmapped code remains visible as `Code N` rather than being guessed, and other unverified TEW IX numeric categories remain unchanged. The label catalog is presentation-only and performs **no MDB migration or write**.

## Historic championship stories and contract creation (unreleased)

**Title Lineage → Edit Selected Reign's Champions** lets you change only the holder UIDs and historical display names in a selected `tblBeltPreHistory` record. **Title Lineage → Insert Historical Reign** adds one dated record without deleting or regenerating the existing reigns; the selected title's `BeltOrder` values are re-numbered chronologically, transactionally, while existing holder IDs, names, capture/loss dates, defenses, UIDs and record names remain unchanged. Both actions require an explicit manual backup. Singles, tag-team and trios title formats use each holder's actual worker UID or **-1 + a historical name** for a name-only NPC. Name-only people are not added to `tblWorker` or `tblTeam`. Examples: Carson and an NPC father may appear as the two tag-team holders; Tavitia and Damien Ward may be recorded as successive historical champions around 2014. Match opponents who did not hold the title are not stored by the title lineage schema.

A new `Workers → Contracts → Create Contract From Template` action can insert one `tblContract` row for the selected existing worker. The user chooses a real existing company and then a real contract from **that same company** as the template, reviews the source fields, and can edit supported terms, including boolean values. The application copies the actual stored template values rather than guessing undocumented TEW IX enum defaults, replaces the worker link and allocates a unique contract UID / Recordname. It refuses a duplicate worker/company pair or incompatible schema, and requires a manual backup and final confirmation. It does **not** modify the source contract or create historical `tblCV` employment. Copying a template is not the same as verifying the business correctness of every original field: use a copied scenario and TEW IX Data Check before relying on these inserts.

**Pending, not mapped:** Body Shape was supplied as 1 Average, 2 Skinny, 3 Toned, 4 Muscular, 5 Ripped, 6 Flabby, 7 Bulky, 8 Obese. An earlier audit observed `tblWorker.BodyType` values 0–7, so those labels are intentionally **not** bound to `BodyType` until the offset is verified. The app must not mislabel code 1 as Average if its actual meaning is different.

## Optional backups and numeric Attributes fix (next update, PR #19)

**Worker Attributes** remain available. TEW IX may store `tblAttribute.Attribute` as a **numeric enum value** rather than a text name. Studio now checks its actual MDB column type, shows raw numeric values as `Code N (unverified)`, and saves typed numeric codes using the exact numeric column type instead of incorrectly inserting text. New/changed numeric attribute selections must use a code already present in the scenario; the application does **not** invent unverified attribute names or translate codes without a verified game mapping. The Hidden/Permanent fields remain separate Yes/No settings, and can use the MDB's verified boolean or numeric flag storage. Original attribute UIDs and worker links remain intact when editing. The numeric-attribute read/write path still needs testing using a copied TEW IX MDB followed by Data Check before use on important scenarios.

**Relationships** and **Create Contract From Template** now offer **three backup choices** when a manual backup has not already been created for the selected scenario: **Yes** creates one before continuing, **No** continues without a backup, and **Cancel** stops the operation. Backups are recommended but not mandatory for these two workflows. Existing confirmation dialogs and database validations remain in place. Other higher-risk operations, including destructive full championship-history replacement, retain their existing backup safeguards.

## Dual-purpose partner text boxes (next update, PR #19)

For Tag Team and Trios history entry, each partner has an **existing worker** dropdown and one adjacent **name field**. When the dropdown is empty, a name is **required** and identifies a name-only historical NPC (holder UID `-1`), available in Build new full history. When a real wrestler is selected, the same field is an **optional ring-name alias** for that person: leaving it blank uses the worker's existing name, while typing a different name retains the real positive worker UID. This permits two or three fully linked workers with independent display aliases and is also valid in safe existing-slot replacement mode. Dynamic field labels and tooltips clarify which interpretation is active.

The independent primary champion's ring-name / name-only entry remains separate. The generator continues to disallow duplicate linked worker UIDs within a team and limits historical display names to 30 characters. No new roster workers or teams are created by alias entry.

## Import custom historical champion names (draft)

In **Titles → Advanced Generator → Build new full history**, the Name / Alias box no longer requires a selected roster worker. Use **Add Name-Only** to add the typed person independently, or **Import Name List** to paste multiple names or read a .txt/.csv file. Singles accepts one name per line (or comma-separated), tag teams accept two names per line, and trios accept three names per line; team entries use / or comma separators. Imported people appear in the editable candidates grid with Worker ID -1; set each entry's required reigns and winning years as desired. The generator uses temporary internal scheduling identities to keep unrelated name-only champions distinct, but stores EVERY unlinked person as UID -1 + historical name in title lineage. No tblWorker, tblGenerateWorker, or tblTeam record is created or modified.

The existing **Add Linked Superstar** button retains the ability to select a real wrestler and enter an alternate ring-name alias. If no wrestler is selected, typing a name also creates a separate name-only historical champion. A name-only primary may hold a tag-team or trios title with a mix of real linked partners and named NPCs. The import generates explicit champion candidates (not merely a background-name pool). These actions require the full-history mode: safe existing-slot replacement still requires linked wrestlers. The preview and destructive-import safeguards are unchanged.

## Full-history generator for Tag Team and Trios titles (draft)

The Advanced Generator's **Build new full history** mode now supports **Singles, Tag Team (2 holders), and Trios (3 holders)**. The original winning-year and reign-duration scheduler still determines capture/loss dates and defenses. For tag teams and trios, each pinned superstar win expands into its full linked team, retaining all real worker UIDs and historical ring names. Partner boxes permit an existing linked worker OR a **name-only NPC partner** (stored as UID -1 plus their historical name); for example Carson can hold the title with his late father without creating a playable roster worker. The unoccupied reigns are populated with distinct name-only NPC pairs/trios sourced from the scenario's tblGenerateWorker names, again without adding tblWorker or tblTeam rows.

The generated preview shows all holder names and UIDs, preserves all partner fields in exported drafts, and verifies employment history for every linked participant. The transactional full rebuild validates all one/two/three holder positions and persists Holder1/Holder2/Holder3 plus their separate display names in tblBeltPreHistory. **Build new full history DELETES and REPLACES the selected title's existing historical reigns only**, so it now requires a manually created backup before import, on top of the destructive confirmation. The existing safer name-only slot replacement stays separate, preserves all original reign dates, and still requires real linked team members. New NPC/reign writes must be tested against a copied scenario and checked in the actual TEW IX Data Check before a public release.

## Relationships editor (development preview)

The Relationships sidebar now browses real tblRelation records with search by worker name or UID, category filters and controls to create, edit, or delete a relationship. Each worker pair has independent personal (P_Rel), romantic (R_Rel), family (F_Rel) and Yes/No Mentor settings; the numeric dropdown choices use the maintainer-verified zero-based labels. Worker1 and Worker2 links are preserved when editing. Reversed duplicate pairs are blocked when creating; unknown existing codes are shown as Code N and remain unchanged unless explicitly replaced.

Every relationship write requires an explicit manual backup, confirmation, and a verified runtime MDB schema. Writes use a transaction and do not alter the worker records. This is under development in PR #18; it is not part of the published v0.1.82 installer. Before using new relationship writes on important data, verify against a copied TEW IX scenario and use the game's Data Check.

## Worker roster filters

The **Workers** sidebar has a collapsible **Filters** panel alongside the existing name/UID search and Name A–Z / Z–A / Worker ID sorting. Filters combine with **AND** logic and update the matching count and worker list immediately. The available controls are: **Active / Inactive**, **Gender**, **Age minimum/maximum** (inclusive, calculated from the worker's `tblWorker.Birthday`), **Current Company** (from live `tblContract.WorkerUID → FedUID` links, including No current contract), **Worker Type / Role**, **Nationality**, **Based-in Region**, and **With pictures / No pictures**. **Reset** clears every filter and the name search to restore the full roster.

Filter values are loaded in a single batch from the selected TEW IX scenario, not from guesswork. Role choices come only from worker-role columns actually found in its `tblWorker` schema; filters unavailable in that MDB are disabled with a short explanation. Verified Gender, Nationality and Based In codes display the app-only labels above while their filter keys remain the original numeric values. Unknown or unsupported codes continue to display as **Code N**. No unverified enum translation is invented. The company filter reads **current contracts**, not historical `tblCV` employment. Portrait presence tests whether a matching file exists in the configured worker-picture folder (or its People subfolder) using the name-first, MDB-filename-fallback rule of the portrait renderer, so blank `Picture` fields can still have a picture. If no picture folder is set, the panel explains why everyone appears to have no configured portrait. Filtering is read-only and never changes the MDB.

## Worker Attributes and Employment History

The **Workers** editor has two additional worker-specific tabs: **Attributes** and **Employment History**.

**Attributes** reads actual `tblAttribute` rows linked by `WorkerUID` and displays their names and `Hidden` / `Permanent` flags. You can add, update, or remove an attribute with explicit confirmation. The selector suggests attribute names already used in the active scenario; typing a new name is possible but Studio warns when it cannot establish that the name is a valid TEW IX attribute. Studio does not silently discard clashing attributes or pretend to know every game attribute definition. Worker IDs, unrelated attributes, and profile fields are preserved.

**Employment History** reads `tblCV` (not `tblContract`) and displays historical company periods with their actual `FedUID`, company initials, `CVFromDate` / `CVUntilDate` and Loan / Trade / Tour / Developmental flags. Users can add, update, or remove individual periods, selecting a valid existing company and specifying the actual dates. The data layer rejects invalid company links, nonsensical dates, duplicates of an identical stint, unsupported schema layouts, and stale database changes. Writes are transactional, confined to the selected worker, and always require explicit confirmation; manual backups remain recommended but optional.

These are direct scenario MDB modifications, so test a copied scenario with TEW IX Data Check before editing important data. The UI does not create active contracts, new workers or companies. Attributes and employment periods have their own Add / Save Selected / Remove actions rather than the main worker scalar-field Save Changes button.

## Tag Teams module

The sidebar now includes **Tag Teams**, integrated into the existing three-column workspace. You can search existing `tblTeam` records, edit their supported fields, and select linked workers and companies from actual `tblWorker` and `tblFed` records. Team type dropdowns show the verified names for codes 1–6 while retaining the **raw numeric codes** for reads and writes. Available type options are still drawn from existing teams in the selected MDB.

**Create Tag Team** opens a dedicated editor for a pair of existing workers, company-specific or game-wide affiliation (using only None codes observed in this MDB), team-type code, experience, formation, finisher, and active state. A manual **Create Backup** is required before creating a team. The app validates the MDB schema, linked IDs and duplicate partnerships, then inserts exactly one new `tblTeam` row transactionally, allocating a unique UID and Recordname. Unsupported mandatory schema fields block creation; no tables besides `tblTeam` are modified.

This initial module must be tested in TEW IX's Data Check using a backed-up scenario before editing your main scenario. Its form fields and mappings may be adjusted as MDB-specific details are validated.

**Repair record names already saved in your MDB (not just new records):** Open a title's **Title Lineage** tab and use **Review / Repair This Title's Record Names** or **Review / Repair All Title Record Names**. In a worker's **Employment History** form use **Review / Repair This Worker's Existing Names** or **Review / Repair All Employment Record Names**. A dark preview shows old and proposed `RecordName` values side by side, including unchanged/unsupported records and any warnings. Nothing is written until the user explicitly confirms the preview. Existing `tblBeltPreHistory` names become `Title Name001`, `Title Name002`, etc., numbered by `BeltOrder`; existing `tblCV` names become `INITIALS (YYYY-YYYY)` with readable ` #2` collision suffixes where necessary. Already-correct names are skipped. Missing initials, unknown/sentinel years or unclear record identities are flagged and remain unchanged, not guessed. The migration updates **only the Recordname/RecordName text column**, preserving record UIDs, title IDs and order, actual title holders, capture/loss dates, defenses, worker and company links, employment dates and flags. To handle cross-renames safely, the write uses unique temporary names and finishes inside a single transaction; stale previews are rejected. Create a manual backup first, and test a copied TEW IX MDB before relying on this migration.

**Readable title and employment record names:** Newly rebuilt full championship histories use the title's actual `tblBelt.Name` plus a three-digit reign number, such as `BCW Championship001`, `BCW Championship002`, etc. Existing title history identifiers are NOT mass renamed. A new historical employment stint uses `INITIALS (YYYY-YYYY)` in `tblCV.RecordName`, e.g. `PWA (2015-2021)`, and gets a collision suffix (` #2`, etc.) only if required to keep that table's identifiers unique. The Employment History form has an editable **Record name** field before the company dropdown, plus a **Generate name** button. Changing an existing record's name is an explicit, worker-scoped transactional update. Manual names are checked for uniqueness and MDB text length; the generated form is still editable.

**Workers → Contracts:** A new **Contracts** tab appears immediately before **Employment History**. It reads linked live `tblContract` entries, with the active company (when its reference is present) and a full per-record field inspector. Supported existing scalar columns may be edited through **Save Selected Contract** after confirmation; the record identity, linked worker and unverified foreign keys remain protected. This intentionally does not create/delete active contracts, whose complete mandatory schema has not been independently validated. Historical `tblCV` periods stay separate. The attribute, contract and historical employment grids now use consistent dark headers, rows, cell selection and text styling rather than the WPF white default.

**Date entry and display:** All human-facing date values now use **MM/DD/YYYY** (for example, **06/09/2002**) in worker profiles, existing-record editors, employment history, tag-team formation, championship lineage and previews, confirmation messages, and CSV exports. Date text fields validate this exact month/day/year order, including two-digit months and days; year-first **YYYY-MM-DD** input is no longer accepted. Worker date pickers remain arranged Month / Day / Year. This affects formatting only: TEW IX MDB columns still store native date values, history calculations are unchanged, and year-only history-range settings remain year-only.

**Visible tag-team dropdown selections:** The shared dark WPF ComboBox template now supports editable text via `PART_EditableTextBox`, preserving selected worker, company and team-type labels while allowing typed searches. The existing Tag Teams editor and Create Tag Team dialog explicitly render the option labels. This is a display and input fix; it does not change saved team IDs or modify MDB data.

## Desktop application

The published Windows app now uses **WPF and .NET 8**. Its source is in `src/TEWUniverse.Desktop`, sharing the existing Access data layer and settings from `src/TEWUniverse.Studio`.

The worker portrait feature looks for a **worker-name PNG first**, then WebP/JPEG/GIF/BMP files in that order, in the configured local pictures folder or its `People` subfolder. If no usable worker-name image exists, it falls back to the stem of the worker's `tblWorker.Picture` filename, with PNG still preferred. Missing images show the silhouette; loaded images hide the silhouette and its background, preserving PNG transparency. Portrait loading never edits the MDB or image files. WebP requires a compatible Windows image codec.

Gender, Sexuality, Pronouns, Race, Nationality, Based In, Wrestling Style, Competes Against and Outside Relationship use verified label dropdowns when their stored codes are recognized, preserving the original numeric values in the editor and MDB. Unknown values remain editable raw codes. Boolean flags such as Active remain Yes/No controls.

The redesigned Workers screen includes a sidebar, searchable worker list, real MDB fields, biography editor and status bar. Companies, Titles (championships), Events, and Stables now have existing-record editors in the same dark workspace. These sections browse existing MDB entries and allow updates to a restricted set of fields. Relationships, History and Tools remain nonfunctional placeholders until relationship and title-lineage operations are validated.

In Titles, open **Title Lineage** to view existing pre-game reigns from `tblBeltPreHistory`, filtered by the selected championship and sorted by Order Number where the MDB schema identifies it. A Generate Title Reigns panel lets you select a pool of existing workers, reign count, years and singles/tag-team mode, then generate a dated preview and export a draft CSV. You can replace holders and dates ONLY when the selected championship already has exactly the same number of prehistory rows; this updates only that belt's existing history UIDs in one transaction. Nothing is inserted or deleted. Always back up before replacing lineage; the exported draft CSV is not a verified TEW IX import file. If the belt-reference column cannot be recognized unambiguously, the app shows diagnostic columns rather than mixing reigns across belts.

Titles now also includes an **Advanced Generator** tab: select existing workers by UID (optionally using historical ring names) or add historical name-only champions with `Holder1=-1`. Specify their eligible years in the company and the exact number of required reigns. The planner reserves these reigns within their eligibility windows, then can fill the remaining slots using eligible background holders loaded from the selected title's existing MDB history. A preview and CSV export work for any proposed number of reigns; applying the draft is restricted to the existing rows of that championship, without inserting records. This advanced generator currently handles singles histories. A manual backup is recommended but optional before replacing records.

**Cross-title tournament chronology:** In the Advanced Generator's Superstars section, the checked-by-default **Schedule title wins after the wrestler's recorded tournament victories** option reads other titles marked **Annual Tournament / Cup** in the active scenario. For each fixed championship-winning year, a matching worker UID and recorded tournament victory in that SAME year constrain the generated title capture to occur AFTER the tournament date. A May 2020 Cup victory therefore prevents that wrestler's 2020 Junior Heavyweight championship run from starting in January. The preview identifies the supporting tournament and date. Disabling the option restores the unconstrained dates; name-only NPC histories (Holder1=-1) cannot be linked reliably and are ignored. Only preview dates for the currently selected title change; other existing lineage is read-only. If the constraints cannot fit in the selected calendar year, generation reports an error rather than quietly violating the chronology. This is an optional storyline rule, not an assumption that winning every Cup guarantees a title reign.

**Singles, Tag Team and Trios lineage formats:** Under **Titles → Championship Details**, the second studio-only classification dropdown (next to Championship / Annual Tournament) chooses how many linked real-worker holders a reign needs: **Singles (1)**, **Tag Team (2)** or **Trios (3)**. The format is stored in local application settings for the selected database/title, not written as an invented TEW IX belt code. Tag and Trios entries accept a primary wrestler plus partner worker UIDs; each member must be a different existing worker. Until full group-history generation is implemented, new full-history building remains singles-only; Tag Team and Trios use the safe existing-lineage substitution workflow.

**Add known champions to an already complete title history:** For a title with existing `tblBeltPreHistory` rows, the Advanced Generator defaults to **Replace only name-only/unused reigns (preserve dates)**. A requested **four-time** champion such as Carson Cade takes up to four eligible name-only placeholder reigns; reigns already linked to Carson count toward his four, so existing champion records are never duplicated or overwritten. Exact winning years and requested day/month/year lengths restrict which existing slots qualify. If no matching unused slots exist, preview fails with an actionable error. Only the chosen existing slot **Holder1/2/3 IDs and names** change; original capture/loss dates, defenses, reign order, UIDs, unrelated NPC slots and linked real-worker champions remain intact. A separate explicit **Build new full history** mode still exists for intentionally rebuilding a singles title (and annual tournament, singles-format winner histories). The importer uses a transactional identity-checked, holder-only UPDATE and a clear confirmation distinguishing patching from deletion/rebuild.

**Employment-history validation:** Both previews compare a linked champion's **full title tenure** with `tblCV` employment for the title's company. The **Employment-check company** selector defaults to `tblBelt.OriginalFed`, but lets you override that when a belt has changed promotions. A reign is marked **Covered** only if documented employment (including contiguous stints) spans the entire capture-through-loss period. Missing CV periods, unknown companies and historical date sentinels are distinctly flagged, not silently ignored or used to change a title's dates. Annual Cup winners are checked on their winning day. Warnings are repeated before importing; backing up first is recommended but optional.

**Flexible superstar reign counts, winning years and durations:** The **Titles → Advanced Generator → Superstars** grid lets you specify a wrestler's **Reigns** independently of **Years won**. Repeated years are valid for ordinary championships (e.g. `2016, 2016` for a title-trading feud); the generator inserts another champion between separate reigns. A 14-time champion does **not** need 14 different years. Enter only the years you know, in chronological order; `-` represents an automatically assigned year in a particular slot and omitted later slots are also filled automatically within the wrestler's **Active from / until** years and the title's history range. Annual Tournament / Cup mode still permits one winner per edition and requires a distinct year for each real-worker Cup win.

**Reign lengths are independently optional per victory:** enter `719d` for EXACTLY 719 inclusive days. Enter `2y` for **at least two calendar years**, with up to 90 additional days when compatible with other known wins; `6m` means **at least six calendar months** plus up to 30 additional days. These are intentionally *approximate* calendar requests, whereas `d` is an exact day count. Specify `2y` for only the first of six reigns and leave the remaining lengths unspecified, or use `-, -, 2y` to target only the third. Other reigns retain randomized lengths. The generator will not truncate a protected tenure to insert an NPC or another known winner and reports infeasible conflicts. The preview shows requested vs actual tenure, and importing remains a separate confirmed action.

**Optional championship starting month:** The Advanced Generator's NPC History section offers **Starting month (optional)** for regular championships. **Default (January)** keeps January as the opening month, but the first championship reign now begins on a **random day** within that month. Selecting June with From year **2002** places the initial PWA World Heavyweight Championship reign on a randomized June date, never before Pinnacle Wrestling Alliance opened. Both the inaugural NPC history and any pinned real-worker wins in the first year respect that boundary; later years and cross-title tournament chronology still work normally. The preview states the resolved first allowed date. Annual Tournament / Cup titles continue to use their separate recurring event month, week and weekday, so the championship-only start selector is hidden for them. The Through year still ends December 31; this change does not add an optional end date. If the first-year schedule cannot fit the pinned wins after the chosen month, the generator rejects it rather than moving them earlier. No existing MDB history changes until you import the preview.

**Varied championship reigns:** Standard championships no longer automatically change hands on January 1 or award every champion an identical year-long reign. The Advanced Generator now picks variable durations—including a few weeks, several months, and occasional reigns lasting more than a year—while preserving every fixed winning **year** supplied for a real superstar. The number of generated reigns emerges from this chronology, instead of one history entry per calendar year. Defence counts are also varied independently of reign duration. The preview shows days held and a short/medium/long breakdown. The older fixed-count generator also allocates its requested number of reigns across uneven durations. **Annual tournaments** produce one winner per year on a date calculated from a recurring schedule (month, first/second/third/fourth/last occurrence, weekday), without a title-loss reign or defences.

**Expanded title editing:** Additional `tblBelt` fields are now real editable controls rather than a read-only list. Settings such as **Annual Title**, **Annual Type**, **Tour Frequency**, **TV Frequency**, **Retain Title**, **Achievement**, **Valid Matches**, and **Belt Lock** can be changed using their stored MDB data types when present. Title UID, internal record names and unknown foreign-key fields remain protected. **Original Fed** and **Card UID** accept existing linked IDs (with zero / -1 unassigned sentinels), checked against `tblFed` or `tblCard` before saving. All edits use the normal Save Changes transaction and pending-change tracking. No automatic backup is created; use Create Backup before editing an important scenario. Title Classification is still a separate cosmetic setting saved locally, not a fake TEW IX enum.

**More varied annual tournament winners:** The Advanced Generator no longer restricts historical Cup NPCs to roughly one recurring name for every three editions. Where `tblGenerateWorker` supplies enough eligible names, at least 75% of NPC-winning editions use **distinct** historical names; the remaining editions allow occasional repeat winners. Repeat wins prefer previously less successful entrants and avoid the last two editions where possible. Fixed superstar victories keep their linked worker UIDs and exact winning years, and tournament dates are unaffected. If the generated-worker source or optional race/gender filters provide too few names, repeats remain necessary and the preview reports the available diversity. Preview also displays the count of distinct NPC winners. Existing title lineage changes only when the user explicitly imports the generated preview.

**Championship vs. annual tournament:** Title Details now has an app-only **Title Classification** selector for each championship UID in each scenario database. The label is saved locally in TEW Universe Studio settings, not written into `tblBelt`. **Championship** continues to show reigns, loss dates, and defences. **Annual Tournament / Cup** represents one winner for each annual edition: the generator asks for the event month and weekday occurrence (for example, the first Sunday in March) and computes `BeltCaptured` separately for each year's edition, and uses the title-history no-reign conventions visible in existing TEW IX data (`BeltLost = 1666-01-01`, `Defences = -1`). The lineage table displays winners rather than treating them as champions with year-long reigns. The old reign-based generator is blocked for tournament-classified titles. The title editor also includes an expanded read-only inspector of other `tblBelt` fields and additional allowlisted descriptive fields; IDs and foreign key relationships remain protected. This is a Studio display classification, not an assertion that TEW IX stores these types itself. Test generated tournament history on a backed-up scenario before writing to the primary MDB.

**Two-section history generator:** In **Titles → Advanced Generator**, the top **Superstars** section contains only linked workers, their optional historical ring names, active years, total reign counts, partially specified winning years (including repeats), and independently optional reign lengths. The lower **NPC History** section contains just the historical start/end years and optional race/gender codes; there is **no NPC reign-count field**. The generator automatically creates a name-only NPC winner in each year without a pinned superstar victory, drawing names from `tblGenerateWorker` and never adding workers. For example, a cup that began in 1994 with Kaito Moriyama's sole 2020 victory produces a full chronology across the chosen years, not a one-row preview. Rebuilding the selected belt requires confirmation and successful schema checks; making a manual backup first is recommended but optional. History inserts have not yet been validated in-game.

**Fixed-win history builder:** The Advanced Generator now accepts exact championship-winning years for linked workers, for example `2016, 2017, 2019` for Dragonheart (`#4975`). It reads name-only NPC candidates from `tblGenerateWorker`, optionally filtering by stored race/gender codes, and generates a chronological sequence with NPC champions before, between, and after those fixed wins. NPC champions are written with `Holder1=-1` and a historical display name; no NPC is added to `tblWorker`. The preview shows the implied predecessor and successor of each champion. A full rebuild can **DELETE the selected championship's old `tblBeltPreHistory` rows and INSERT any requested number of new rows in one transaction** (other championships and workers are not changed). The **Import Preview to Title Lineage** action performs this destructive replacement for the selected title only, recommends an on-demand **Create Backup** but requires only explicit destructive confirmation, then opens the saved Title Lineage view so the results are immediately visible. The table schema is validated at runtime, and unsupported schemas fail without writing. Validate a test database with TEW IX's Data Check before editing production data.

**Direct database editing:** Select an existing scenario MDB as the **Active Database**. Save Changes writes to that same file; Refresh Database reloads records added or changed externally. There is no required working copy. **Create Backup** is a separate manual snapshot. **Export Copy As** creates an independent MDB without changing the active selection. Legacy Default Database and Current Copy paths are not automatically activated after upgrading: explicitly choose the MDB you intend to edit. If the file changes externally after opening, saving is blocked until you refresh. Close TEW IX\'s database editor while using this application; do not edit the same MDB simultaneously. **No entity insert or delete operations are performed.** Existing IDs and linked references are protected.

## Distribution

Get the Windows installer from [GitHub Releases](https://github.com/TheImposter1000/TEW-Universe/releases). GitHub Actions builds WPF, the installer and update agent. Microsoft ACE OLE DB for 64-bit Windows is required for Access MDB connections.

The explicitly selected scenario database is edited directly. Credentials are not in source code; optional password remembering uses local Windows-user DPAPI encryption.
