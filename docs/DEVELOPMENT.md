# Development and compatibility

## Verified application-only code labels

`TewCodeLabels` is a centralized catalog of maintainer-provided TEW IX enum labels. It maps `tblWorker` fields Gender (8 codes), Sexuality (5), Pronouns (5), Race (9), Based_In (65), Nationality (200), Style (16), CompetesAgainst (5), and Outsiderel (4), plus `tblTeam.Type` (6), plus three zero-based relationship fields (P_Rel 9, R_Rel 7, F_Rel 7), plus 57 sparse `tblAttribute.Attribute` mappings (Personality 1–28, Alignment 310–315, Gimmick 320–339 and Other Performance 374–376), for a total of 403 codes across fourteen database fields. The WPF worker profile, Quick Facts, gender/nationality/region roster filters, tag team editors, Create Tag Team dialog and legacy Windows Forms worker profile use these labels only for presentation. The source numeric values remain the editor's draft values, filter keys and actual MDB values. Unknown codes retain the `Code N` fallback; no MDB table, column or record is altered by the mapping feature. Tests cover the contiguous code ranges, all 403 numeric code round-trips, mapping spot checks, all five Competes Against options and four Outside Relationship options, unknown fallbacks and category isolation. Most ordered label sets use their 1-based line position; the three relationship sets explicitly use zero-based positions, beginning with None. Attribute codes are non-contiguous and retain their exact explicit number. Code assignments must not be reordered without verification.

## Historic title lineage and copied contract insertion (unreleased)

The `HistoricalLineageSession` service updates a selected `tblBeltPreHistory` holder trio without changing its dates or identity, or inserts one new chronological reign. Each active participant position is a linked worker (UID greater than zero) **or a name-only NPC** (holder UID `-1` and `Holder_NameN`). The pure `HistoricalReignRules` rejects invalid/duplicate linked UIDs, empty names, and overlapping capture/loss spans. The insertion adjusts `BeltOrder` only within the selected belt via transactional two-stage reindexing to avoid sequence collisions, and does not delete other reigns or create `tblWorker` records. The UI offers a manual backup choice before either action, but does not require one; this code still needs scenario-copy testing and TEW IX Data Check. The story use case is Carson as a real worker partnered by his father as a name-only NPC; the 2014 Tavitia/Damien Ward history can use linked and/or name-only holders if the title's recorded reign dates permit insertion. Ordinary match opponents who never held that belt are not captured by `tblBeltPreHistory`.

`WorkerContractCreationSession` accepts a real same-company source `tblContract` record as a complete template, verifies its identity/schema/current fields and the target worker/company, checks for an existing contract with that company, and copies source values before applying changed supported fields. It allocates a new UID/Recordname within a transaction. This deliberately avoids assuming undocumented contract enum defaults or treating all numeric fields as code labels. It refuses schema mismatches and offers an optional backup in the UI. Unknown fields may still have game-specific semantics, so new contracts must be tested on a copy with TEW IX Data Check before production use.

Pending verification: the user supplied an eight-item Body Shape enumeration numbered 1–8; the observed `tblWorker.BodyType` range includes 0 and lacks 8. The app does not bind these potential labels until this offset discrepancy is resolved.

Multiple selected conditions are ANDed (alongside existing case-insensitive name/UID search), and the existing sort is applied afterward. Ages use the calendar date in the running Windows environment; unknown, future and sentinel birth dates cannot match an explicit age bound. The age editor accepts only 0–120 and flags a reversed or invalid range rather than silently ignoring it.

`DatabaseSession.ReadWorkerFilterIndex` reads only worker IDs and verified `tblWorker` fields (Active from the existing catalog, Gender, Birthday, Nationality, Based_In and known role-flag fields actually present in the runtime schema). A separate batched `tblContract.WorkerUID/FedUID` scan supplies **current company** membership, including multiple simultaneous employers. Missing or incompatible role/company data disables those filter choices; verified Gender, Nationality and Based In codes show labels with their original `Code N` keys retained for filtering. The actual picture lookup is deferred until a Pictures/No Pictures filter is requested to avoid decoding thousands of roster portraits. The filter feature makes no changes to external image files or MDB records. Pure regression tests exercise combined gender/age/status/role/company/nationality/region/picture conditions, overlapping companies, worker UID search, and age boundaries.

## Consistent user-facing date format

The shared `StudioDateFormat` helper outputs `MM/dd/yyyy` while accepting US numeric month/day/year with one- or two-digit month/day, plus written English month names and correctly matched ordinal suffixes. `5/12/1998`, `05/12/1998`, `May 12th 1998` and `May 12, 1998` map to the same `DateTime`. Invalid dates, incorrect ordinals, ambiguous non-US numeric formats and year-first `2002-06-09` are rejected. `DatabaseSession.Display` and `DatabaseSession.Parse` use the helper; MDB storage remains typed `DateTime`, never a SQL date literal. Existing-record editors, employment history, team formation dates, contract editing and creation, title previews and CSV import use the same parsing rule. UI display and CSV export retain `MM/DD/YYYY`; separate worker Month / Day / Year selectors are unchanged.

This change does not reformat backup filenames, serialized release metadata, or annual-tournament date arithmetic. It does not convert plain history range **years** into full dates. Regression tests check written and numeric equivalence, ordinal validity, leap days, sentinels, year-first rejection, and semantic contract change detection.

## Repair already-persisted RecordName values

`RecordNameRepairPlanner.Titles` plans a deterministic mapping from each selected title's existing `tblBeltPreHistory` UID/BeltUID/BeltOrder/`Recordname` to `tblBelt.Name` + three-digit per-title sequence, respecting historical order, protecting names belonging to unrelated titles, and skipping rows with missing identities/title names. `RecordNameRepairPlanner.Employment` plans `tblCV.RecordName` values from the **record's own** `Initials`, `CVFromDate`, and `CVUntilDate`. A duplicate year-range stem receives a readable ` #2` etc. suffix, including conflicts with other workers' records. Records with unknown 1666 sentinel years or invalid dates remain unchanged with a visible warning. Duplicate current `RecordName` keys abort preview instead of risking ambiguous row identification. Both planners support single title / single worker **and** database-wide preview scopes.

`DatabaseSession.PreviewTitleRecordNameRepairs` and `PreviewEmploymentRecordNameRepairs` read existing MDB identities and build *read-only* proposed changes. `ApplyRecordNameRepairs` repeats the plan, checks that row counts and proposed identities still match the preview, validates schema and MDB max text lengths, checks target uniqueness against records outside the migration, calls `EnsureUnchanged`, and performs all renames under **one OLE DB transaction**. Each selected row is constrained by its verified UID/BeltUID/BeltOrder and old Recordname (titles) or WorkerUID/FedUID/from/until/old RecordName (historical employment). All changed names are first moved to unique short temporary identifiers to permit swaps without Access unique-index collisions; final names are applied only after staging succeeds. Any mismatch/constraint error rolls back the entire set. Neither operation uses `DELETE` or `INSERT`, and no holders/dates/defenses/contract data/worker links are edited. A WPF modal dialog shows old/new names and requires a further destructive-write confirmation; the *manual* database backup is strongly recommended but not automatic.

`RecordNameRepairView.cs` provides scoped and global actions under Title Lineage and Worker Employment History. Existing correct names remain untouched. Tests cover selected and global scopes, name collisions across titles/workers, pre-existing proper names, swapped historical names, unknown employment dates and duplicate identifier rejection. Physical MDB/TEW IX Data Check is necessary before adopting the migration in a primary scenario; automated tests cannot verify in-game string-reference behavior.

## TEW-style RecordName conventions and active worker Contracts

Full rebuilds of a singles `tblBeltPreHistory` title now derive `Recordname` from verified `tblBelt.Name` and the next available zero-padded three-digit ordinal, e.g. `BCW Championship001`. Names are checked globally against every *other title's* prehistory records and against names already allocated in the current transaction; the original belt and other titles remain untouched. Targeted name-only holder substitutions preserve ALL existing `Recordname` values. A full rebuild intentionally replaces the selected title's prehistory; it never bulk-renames unrelated history records.

The `EmploymentNameGeneration.Validate` helper provides precise field-specific validation for Generate name, distinguishes missing/invalid From and Until dates, checks 1800–2100 limits and chronological order, and produces `INITIALS (YYYY-YYYY)` or `INITIALS (YYYY-Present)` as appropriate. `StudioDateFormat.OngoingEndDate` is exactly `01/01/1666`, recognized only in the correct end-date contexts; this sentinel is never a permitted employment From year. The WPF editor presents its error inline and focuses the field, rather than displaying one catch-all message. Manual edits and existing records are preserved; a blank initials field can be populated from the selected company's stored `tblFed.Initials`, never a guessed abbreviation. Both complete dates remain required.

New `tblCV.RecordName` values use `StudioRecordNames.Employment(initials, from, until)`, e.g. `PWA (2015-2021)`; a generated collision is resolved with a readable ` #2` suffix if within the actual MDB max length. The Employment History form puts the **Record name** text field before the company selector, supports manual edits, and regenerates a name on demand. Changing a saved record's identifier is a single-row `UPDATE ... WHERE RecordName=? AND WorkerUID=?` within the same transaction that updates its dates and linked company. Blank/manual conflicting names, unsupported column types and oversize strings fail closed.

The **Contracts** tab in Workers is a separate `tblContract` record viewer/editor; it does not use historical `tblCV` data. The data layer inspects `tblContract` for a verified integer `WorkerUID` and a unique record key (`UID` or `Recordname`), reads only rows belonging to the selected worker, and shows their actual stored fields. Editable fields must be supported primitive date/text/numeric/boolean columns; contract identity, worker/federation foreign keys and unverified `*UID` fields are protected. Saving requires confirmation and runs a transactional optimistic row snapshot verification, then field-specific parameterized updates constrained by both the worker link and record identity. Dates accept numeric and written US dates while displaying `MM/DD/YYYY`. The app does **not** fabricate new active contracts or delete existing contracts without a verified complete insertion schema. Runtime schema mismatches show an error in the Contracts tab and do not modify the MDB.

All linked-record DataGrids are styled explicitly with dark column headers, alternating rows, dark selection, and light text to avoid the framework's default white header/cell templates. Pure regression checks cover record-name formatting and invalid employment-year ranges; Windows CI compiles the WPF editor and related date/history checks. Game-side Data Check on a disposable MDB is still recommended after writing an unfamiliar TEW contract value or renaming a historical `RecordName`.

## Worker Attributes and Employment History

The Workers workspace now exposes separate **Attributes** and **Employment History** tabs.

The `tblAttribute` schema has `UID`, `WorkerUID`, `Attribute`, `Hidden` and `Permanent`. The application queries the physical Access field types and supports both textual and integer-backed Attribute columns. For integer-backed scenarios, `TewCodeLabels` supplies 57 maintainer-verified code/label mappings in four disjoint groups: Personality 1–28, Alignment 310–315, Gimmick 320–339, Other Performance 374–376. Five Personality codes (6, 13, 17, 20, 23) are explicitly `Unassigned`; they must remain recognized/readable but cannot be newly assigned. Exactly 52 named, mapped codes are selectable for INSERT or replacing a different attribute code. Unknown codes remain visible as `Code N (unmapped)` and may be preserved on the SAME existing row, including for editing Hidden/Permanent flags; they cannot be assigned to a new row or substituted for a different code. The dropdown uses `WorkerAttributeOption.StoredCode` separately from its human-readable `DisplayText`. `WorkerAttributeValue.Parse` enforces the actual integer MDB type and `SaveWorkerAttribute` double-checks verification before opening the transactional writer. No text label is ever stored in a numeric field.

Worker-constrained `UPDATE` and `DELETE` statements, or a new UID allocated during transactional `INSERT`, protect unrelated workers. The database layer validates distinct attribute assignments and Yes/No flag types, and uses the MDB external-modification guard. Attribute clashes/incompatibilities may still exist and are NOT known from the code list; final testing requires an expendable scenario copy and TEW IX Data Check.

The verified historical employment table is **`tblCV`**, not the active worker contract table `tblContract`. The supported columns are `RecordName`, `WorkerUID`, `FedUID`, `Initials`, `CVFromDate`, `CVUntilDate`, `Loan`, `Trade`, `Tour`, and `Developmental`. Reading displays only the selected worker's periods and resolves `FedUID` against the existing company catalog; orphan company IDs remain visibly labeled. The UI loads a schema-checked `tblFed.UID / Name / Initials` lookup once per employment refresh. Choosing a company overwrites the input with its stored initials, and typing an exact unique initials match chooses that company by UID, case-insensitively. Ambiguous matches never choose a company arbitrarily, and a partial/unknown abbreviation clears stale company selections. Existing historical initials remain unchanged on initial load. Creation and editing require a valid company UID and dates in a supported calendar range, retaining historical initials and the four flags. An employment `CVUntilDate` of `01/01/1666` represents an ongoing stint and is permitted even though it precedes the start chronologically; the raw sentinel is persisted to Access and can be set through a dedicated Still active button. `CVFromDate` cannot use the sentinel. The list shows Ongoing, generated RecordNames use Present, and championship employment verification treats an ongoing stint as covering finite historical reign dates. A company's `CompanyClosing` with this value already means the company is still open. `tblTeam.Active` remains a separate boolean flag, and `tblTeam.Formed` does not become an ongoing end date. An `INSERT` allocates a unique internal `RecordName`, and all `UPDATE` / `DELETE` operations are qualified by both `RecordName` and `WorkerUID` to protect other worker records. A duplicate identical worker/company/date-range period is rejected. Unsupported mandatory fields fail closed.

These linked-record editors have their own explicit Add / Save Selected / Remove buttons and destructive confirmations; they are **not** included in the core worker scalar Save Changes action. A manual backup is recommended, not required. These operations still need TEW IX in-game Data Check and UI verification with a disposable working copy of a scenario, particularly for unknown custom attribute names or rare historical employment sentinels.

## Cross-title championship chronology

The Advanced Generator has a checked-by-default **Schedule title wins after the wrestler's recorded tournament victories** setting for regular championships. The app reads existing `tblBeltPreHistory` for OTHER titles in the current scenario that the user has classified locally as `AnnualTournament`. It only matches positive `Holder1` worker UIDs and the same calendar year as a linked worker's exact requested championship-winning year, using `BeltCaptured` as the tournament-winning date. A historical alias remains safe because matching is by worker UID, not display name. The selected title's generated date cannot fall on or before the prior tournament win. If several Cup wins occur that year, the latest wins. The underlying scheduler preserves chronological order and at least seven days between fixed wins, reporting infeasible year-end constraints rather than omitting them.

This is an **opt-in/out creative chronology assumption**, not a statement of game rules. Classifications are app-local, so unclassified tournaments and name-only NPCs (`Holder1=-1`) are not used. Other championship histories are read but **never written** by this feature. Preview shows the tournament name and original date for affected wins; turning the option off allows the usual unconstrained generated dates. The rule has no effect on the annual tournament generator itself or on title wins pinned to different years. Test import in a disposable TEW IX scenario as usual.

## Title holder format, employment validation and selective lineage substitution

The Title Classification area has separate **record type** (Championship / Annual Tournament) and **competitor format** (Singles / Tag Team / Trios) dropdowns. `AppSettings.TitleCompetitorFormats` stores format as a studio-only database-path/title-ID key, independent of `TitleDisplayKinds`. The dropdown controls whether the Advanced Generator needs 1, 2 or 3 linked worker UIDs per reign; partner UID fields become visible for teams/trios. The existing automatic *full history* planner is verified only for singles. Until a dedicated multi-member full history planner exists, destructive team/trio creation is blocked explicitly; existing team/trio histories can be augmented safely.

When a selected title already contains prehistory, the Advanced Generator defaults to **Replace only name-only/unused reigns**, not Delete+INSERT. `ExistingTitleSlotPlanner` interprets each requested reign count as the **total** champion victories, including any slots already linked to that worker/team. Individual supplied winning years and duration conditions filter eligible existing NPC placeholders; unsupplied years remain flexible within the row's Active from/until years. Multiple wins in one year and a protected different champion between those wins remain possible. A matching algorithm chooses distinct slots, prioritizing verified title-company employment, and fails if there aren't enough compatible name-only records. It **never** chooses a row with any positive existing `Holder1`, `Holder2` or `Holder3` UID, and rejects title competitor-format mismatches.

`DatabaseSession.PatchTitleLineageSlots` checks the exact `BeltUID/BeltOrder` schema and selected row identities, revalidates all linked worker UIDs and expected unlinked holders, and updates **only six holder ID/name columns** within one transaction. It does not update `BeltCaptured`, `BeltLost`, `Defences`, `Recordname`, `UID`, `BeltOrder`, any unrelated slot or another belt. A stale MDB or changed row rolls back the whole operation. A separate manually selected destructive rebuild is still available for singles with an explicit confirmation and optional backup guidance. Preview and targeted CSV export identify which slots would change before import.

`TitleEmploymentValidator.Check` compares each linked worker's entire title tenure against their `tblCV` periods for the selected title company; adjacent documented periods may cover a tenure. With no company override it uses `tblBelt.OriginalFed`; when a title has transferred, an override is available in the Advanced Generator. Annual tournament winners require only the winning date to be covered; the special 1666 `BeltLost` sentinel is not treated as an actual employment end. Missing historical employment, unknown target company, and incomplete/1666 CV dates produce **visible flags** in the preview and a warning in the import confirmation; warnings are advisory, never silent database edits. The app does not assume a missing CV record proves the wrestler never worked there. Regression tests cover a four-time champion, existing linked reigns already counting toward the requested total, an impossible anchored win or exact tenure, tag/trios linked member counts, and full/partial/unverifiable CV coverage.

## Repeated same-year championship wins and optional approximate reign lengths

**Championship** (not Annual Tournament) mode no longer requires one unique year for every reign. The grid's **Reigns** count controls the total number of victories that the generator must assign to each linked worker within the intersection of their **Active from/until** window and the selected title's years. The **Years won** field is a partial, chronologically ordered specification: `2016, 2016` requires two captures in the same year; `2011` with six total reigns pins the first to 2011 and generates five later victories; `-, -, 2011` pins the third, allowing earlier unspecified victories. Unspecified slots are sampled and sorted within their feasible year intervals, and a candidate is retried up to 100 times if random placement conflicts with existing pinned dates or reign-length constraints. Identical worker/year anchors are now legal for regular titles; a different holder must appear between their reigns. Annual Cup mode is unchanged: only one winner per edition, and exact winning years are required.

**Reign lengths** are independently optional and positional. `719d` or `719 days` denotes EXACTLY 719 inclusive held days, so `BeltLost = BeltCaptured + 718 days`. `2y` denotes a *minimum* of two calendar years (`Captured.AddYears(2)`) plus a randomly chosen overrun of 0–90 days if space permits, while `6m` denotes `Captured.AddMonths(6)` plus 0–30 days. A blank token, `-`, or `random` preserves standard varied tenure length; an omitted trailing duration is also random. All optional durations are mapped to the corresponding winning-year position, not to a year-unique lookup. The scheduler first reserves mandatory minimum tenure, applies tournament-based earliest-capture constraints and the history opening month, then chooses a feasible randomized capture date and allowable soft-duration overrun. Other fixed wins and the timeline end are not moved; impossible constraints fail rather than silently shortening a mandatory tenure. The preview identifies both requested durations and actual inclusive **Days held**. This feature controls title tenure only, not a separate undefeated-streak statistic.

**Starting month** is an opening-month window, not a fixed first-of-month date. The initial championship capture is sampled on a random day within that month (January if no month selected). Later reigns retain the varied transition scheduler; this does not alter annual Cup event dates. Regression tests cover varied opening days, repeated same-year linked-worker wins, 14 wins across fewer than 14 years, partially pinned dates and durations, 719-day exact records, approximate two-year and six-month tenures, pinned conflicts, and the annual Cup one-edition-per-year invariant.

## Optional championship opening month

For **Championship** titles, the Advanced Generator displays **Starting month (optional)** in the NPC History section, next to From year and Through year. Default (January) retains January as the beginning month. The inaugural capture is **randomized within the chosen month**, rather than always using the first calendar day. Choosing February through December constrains the opening to that specific month in the **From year only**. For example, From year 2002 + Starting month June creates an earliest legal capture of **2002-06-01**, suitable for Pinnacle Wrestling Alliance's June 2002 founding. The initial NPC reign (if any), the full varied-reign timeline, and the first-year pinned superstar winning years all honor the month boundary, with an opening date randomly chosen inside the month. The pinned-win scheduler also considers any same-year earlier tournament victories, using the **later** of those conditions. If multiple pinned wins cannot fit, it reports an error rather than placing champions before the title existed. Changing month invalidates an outstanding preview; switching titles restores Default (January), avoiding accidentally reusing another belt's founding month.

The month selector is hidden for **Annual Tournament / Cup** titles, which retain the month/week/weekday edition-date scheduler. Later years are unaffected. The existing Through year behavior remains **December 31**; a precise closing event date (such as December 12, 2021) is not implemented here. The normal preview and transactional import workflow is otherwise unchanged. Tests cover a 2002–2021 June-opened championship with and without pinned winners, January-default compatibility, fixed-year spacing, invalid months, and tournament-date independence. This feature is only a generator rule; no TEW IX schema or persisted application settings change is required.

## Annual tournament winner diversity

`AnnualTournamentWinnerPlanner.FillWinners` builds a chronology from the available distinct `tblGenerateWorker` names, preserving every pinned real-worker winner. For NPC editions, the generator aims for a **minimum 75% unique names** when the eligible NPC source supports that amount. The remaining slots are dispersed through the chronology as occasional repeat victories; repeat winners are selected among the least-decorated previous NPC winners and avoid the previous two tournament editions where possible. This fixes multi-decade tournaments becoming dominated by only 3–5 rotating names, while retaining plausible two-time winners. Small source pools and restrictive race/gender filters legitimately limit the number of possible unique winners. No workers are created, no stored tournament histories are read or modified by the picker, and ordinary championship reign generation is unchanged.

The preview reports distinct NPC names versus total NPC winners and explicitly notes insufficient name diversity when filters restrict the pool. Regression tests reproduce a 2005–2021 annual Cup with fixed 2014 and 2018 linked winners, check a large source across randomized seeds, verify that pinned winners and dates stay separate, and cover an intentionally small source list.

## Annual tournament calendar dates and lineage import

For an **Annual Tournament / Cup** title, the Advanced Generator no longer asks for a fixed winning day number. Choose a month (1–12), week of month (First, Second, Third, Fourth, or Last), and weekday (Sunday through Saturday). Every historical year resolves its own valid date, allowing events that always occur on a given weekday. For example, First Sunday of March produces **1994-03-06** and **1997-03-02**. The first four occurrences always exist, and Last selects the last matching weekday of the month. Changing the calendar controls invalidates the current preview.

**Import Preview to Title Lineage** uses the existing transactional `RebuildTitleLineage` path to replace `tblBeltPreHistory` rows only for the selected title. A manually created backup is recommended but optional. Schema checks, unchanged-file checks, and explicit destructive confirmation remain mandatory. After importing, the app switches to Title Lineage and reloads the saved entries. Annual tournaments retain `BeltLost = 01/01/1666` and `Defences = -1`. A CSV export is still only a draft, **not** an import format; the import button writes the current in-memory preview to the selected scenario MDB. Test a disposable scenario in TEW IX Data Check before using production data.

### Advanced Generator: worker tenures and exact reigns

The third tab in **Titles** is **Advanced Generator**, separate from the original generic Title Lineage preview. It uses existing workers from `tblWorker`, including their numeric UIDs, and also accepts name-only historical holders without any worker record (`Holder1=-1`). The history display name can differ from the worker's current MDB name, so historical gimmicks and aliases are preserved. **Load Recorded Holders** builds a background candidate pool from that championship's own `tblBeltPreHistory` entries, respecting each recorded holder's UID where one exists.

Each row in the candidate list has a history name, an optional linked worker UID, a first and last eligible year at the company, an **exact number of required reigns**, and a **Fill gaps** flag. The constrained generator places required reigns only in eligible years, attempts to spread multiple reigns throughout a worker's tenure, and optionally fills all unassigned reign positions using eligible background holders. Example: Dragonheart (worker #4975) could be guaranteed **three reigns in 2016–2021**, while other historical holders fill the remaining title chronology. The work-period dates are entered by the user, not inferred as facts from worker records. Preview and CSV export never write to the MDB.

As with the original generator, the apply action updates the selected belt's existing `tblBeltPreHistory` rows **only when the draft reign count exactly matches existing slots**. History UIDs, BeltUID and BeltOrder remain unchanged; no new records are inserted or borrowed. Real worker UIDs are verified against `tblWorker`, while name-only champions intentionally use the TEW convention `-1` and a populated holder-name field. An existing worker can use a historical alias in that field. The current constrained generator handles singles; it does not overwrite existing tag-team reigns. The button requires confirmation, and creating a separate backup is optional. In-game compatibility of generated dates and history requires testing against a sacrificial scenario before production use.

### Championship reign variety

The Advanced Generator now takes a different path for **Championship** titles than for **Annual Tournament / Cup** labels. For a normal championship, each real superstar's pinned winning **year** is preserved, but the precise capture date within that year is distributed across the calendar. The remaining holder transitions are generated from weighted duration tiers (roughly 2–6 weeks, 1–3 months, 3–8 months, 8–15 months, and occasional 15–25 month reigns), rather than rigid January-to-December cycles. Generated NPCs can recur after intervening reigns but do not receive new `tblWorker` records. When the same linked worker has several pinned victories, an intervening different champion is required so they become separate reigns. The timeline remains chronological and nonoverlapping, with `BeltLost` one day before the next capture and the final holder's history extending through the chosen end year. Defence counts use variable duration-sensitive ranges, not a universal fixed rate. The generator still honors its 500-record safety cap.

In the **legacy fixed-count** generator, randomly weighted reign durations are normalized so exactly the requested number of reigns covers the user-selected dates without equal division. Previews show each reign's **Days held**; the advanced preview also summarizes short, medium, and longer-than-one-year reigns. Rerunning Generate can produce a different plausible history without writing to the MDB. These are fictional history heuristics, not recorded TEW IX results.

**Annual Tournament / Cup** is intentionally excluded from this algorithm. Tournament history still uses one winner per calendar year on an event date calculated using its selected month, ordinal weekday occurrence (first through fourth, or last), and weekday, with `BeltLost = 1666-01-01` and `Defences = -1`. Rebuild actions remain destructive for the selected title's existing history and retain explicit confirmation and recommend an optional manual backup. Verify on a disposable MDB before applying.

### Editing additional championship fields

All additional supported scalar `tblBelt` fields are editable in **Championship Details → Additional TEW IX title settings**. Fields are detected from the selected MDB's schema, and each field retains its stored .NET/OLE DB type. Boolean flags get Yes/No controls, numerical TEW IX codes remain raw editable values, and text/date fields retain their original values until the user changes them. Edits are included in the ordinary dirty-check, Save Changes, and transaction flow; no direct writes occur from typing into a control.

The `UID` primary key, internal `Recordname`, unsupported/binary or calculated fields, and unknown `*UID` / `*_ID` references remain in a smaller read-only group. The two recognized references, `OriginalFed` and `CardUID`, are editable but must reference existing IDs in `tblFed` or `tblCard`, or an explicit unassigned sentinel (0 / -1). The app confirms if a linked ID is being changed; it does not create missing companies/events. This title setting editor is different from the **Title Classification** selector, which is app-only and never changes a TEW IX type column.

This functionality writes to the selected active MDB. A backup is recommended but never a prerequisite; validate changes through TEW IX's Data Check where applicable.

## Championship details and presentation classification

The Titles editor now exposes all additional `tblBelt` columns through an expandable **Additional TEW IX fields** inspector, with protected IDs/references read-only. Basic text/description columns from a strict allowlist are editable when present; the app does not enable arbitrary linked-field editing.

The **Title Classification** control offers **Championship** or **Annual Tournament / Cup**. It is *app-only*, keyed by database filename/path and `tblBelt.UID` in `settings.json`; there is no new type column and no change to existing TEW IX numeric enums. The label persists across launches and survives other settings changes. Championship previews generate ongoing reign records. Annual tournaments generate winners rather than ongoing reigns: one winner per calendar year (unless a championship title is selected), a recurring event schedule (month, week-of-month occurrence, weekday) that computes a distinct date for each year, `BeltLost = 1666-01-01`, and `Defences = -1`, matching the sentinel convention observed in the provided TEW IX screenshot. The tournament viewer omits these no-reign fields, relabeling winning dates and holders. This is not a guarantee that every scenario uses the same sentinel semantics; test in TEW IX Data Check using a disposable MDB before rebuilding any production title history.

The legacy reign-based generator remains for championship titles only. Rebuild operations still delete/reinsert only the selected `tblBeltPreHistory` rows transactionally, and require explicit confirmation; a manual backup is recommended but optional.

### Superstar and NPC history sections

The Advanced Generator interface is deliberately separated into two areas:

- **Superstars (top):** Linked `tblWorker` entries. Add a worker by name or UID, optionally specify a historical alias, then enter the worker's eligible years and total championship reign count. Winning years and lengths are independently optional by position: an omitted year is assigned inside the valid active window and a repeated year is allowed. User-pinned dates, if supplied, remain fixed; annual Cups still require a distinct year per edition. A single-year eligible window starts with one win prefilled.
- **NPC History (bottom):** Only the historical first and last year, plus optional exact race/gender codes. All usable names come from `tblGenerateWorker`; there is no manual NPC roster or NPC reign-count field. The generator fills each otherwise-unassigned calendar year using a recurring set of generated historical names. Those NPCs remain `Holder1=-1` in `tblBeltPreHistory` and never appear in `tblWorker`. Generating an entirely name-only history is permitted.

Unlike the previous advanced editor, the total history-row count is derived from the protected human victories and varied background reigns; users do not need to count NPC reigns. Annual Cups generate exactly one edition per year, while ordinary championships can contain several reigns within one calendar year. Generated inaugural dates are randomly placed inside the selected opening month. Repeated victories by the same linked worker are separate records with an intervening champion. The preview labels previous and next winners rather than asserting how title changes happened in actual matches.

Rebuilding remains destructive **for the selected championship's existing prehistory only**, is guarded by explicit confirmation; creating a manual backup first is recommended but optional, and needs TEW IX compatibility testing on a disposable MDB. These changes do not affect the separate original generic generator in the Title Lineage tab.

### Pinned winning years, generated NPCs, and creating new title history

The **Advanced Generator** provides a `Years won` cell for linked workers. Supplied years (for example `2016, 2016, 2019`) are non-negotiable anchor events; omitted or `-` positions are assigned automatically within the worker's eligible years. The generator plans title changes before, between, and after those specific victories. It uses `tblGenerateWorker` for an NPC naming pool (with optional exact race and gender code filters), not `tblWorker`; NPCs exist **only in title history**, as `Holder1=-1` with the display name. A linked worker such as Kaito Moriyama #4975 can use the historical ring name Dragonheart.

The planner fills other historical reigns with a recurring cast of generated NPCs and shows implied title changes in a preview. These are implied by consecutive holders, not explicit match results in the MDB. The existing generic generator is retained for non-anchored workflows. Generated names are loaded from the actual MDB schema. A missing or unrecognized source-name field produces an error with available columns; field names or numeric code legends are never invented.

Applying an anchored draft **replaces the selected championship's complete title prehistory**, even if the new number of reigns differs from the old number. It deletes `tblBeltPreHistory` rows only where `BeltUID` matches the selected title, then inserts new rows with unique `Recordname`, `BeltOrder`, holder names and IDs, win/loss dates, and defences in **one database transaction**. It does not insert or modify worker records, change other titles, or create companies. The application checks the schema and file modification stamp, offers an optional **Create Backup** choice, and shows a separate irreversible replacement confirmation before committing. On a failed insert, it rolls back the transaction. All regeneration should first be tested against a backed-up TEW IX scenario; MDB structure and game-side behavior still require on-device validation.

## Title lineage and bounded generator

The Titles workspace includes **Championship Details** and **Title Lineage** tabs. Lineage reads `tblBeltPreHistory` directly. Order Number is applied when a recognizable numeric order field is present. The read-only grid exposes the actual MDB columns rather than inventing holder names or dates. If the relation cannot be established, it explains which columns were found and shows no rows; other championships' histories must never leak into the selected one. The supplied TEW IX database schema confirms `BeltOrder`, `Holder_Name1`/`Holder_Name2`/`Holder_Name3`, `BeltCaptured`, `BeltLost`, and `Defences`. A generator now produces a preview from a user-selected pool of existing workers, a date range, and single/tag mode. Applying a preview is an explicitly confirmed, transactional update of **every already-existing history row of the selected championship only**. Row UIDs, BeltUIDs, BeltOrders and Recordnames remain intact; there are no INSERT or DELETE operations. A generated count different from the number of the title's pre-existing slots can be exported as a draft CSV but cannot be applied to the MDB. ## Existing-record module expansion

The integrated WPF workspace now supports repurposing **existing** company, title, event and stable entries without creating new TEW IX records. Modules use `tblFed`, `tblBelt`, `tblCard`, and `tblStable` respectively, each keyed by existing `UID`. ## Scope of current MVP

The editor updates **existing** workers, companies, championship titles, events and stables. It displays raw data fields where TEW-specific value mappings are not yet established. It never inserts worker records. It searches tblWorker, and reads tblWorkerSkill, tblWorkerOver, tblWorkerPhysical and tblWorkerBio via existing WorkerUID/UID keys. Linked rows that do not exist are left untouched. Brand-new record creation, title lineage generation and advanced game-specific validation are not supported.

## Active database workflow (direct edit)

TEW Universe Studio now works directly with **one explicitly selected scenario MDB**. Choose **Select Database** to open it (or choose it through **Settings → Active Database**). **Save Changes** modifies that file in place, using parameterized transactions. **Refresh Database** closes and reopens the data session to load records added or edited outside the application. Avoid concurrent editing: close TEW IX's own database editor before using TEW Universe Studio, and close TEW Universe Studio before editing the file in TEW IX.

**Migration is explicit:** settings from older versions still load, but the previous **Default Database** and **Current Copy** paths are not silently promoted to the Active Database. Select the actual MDB intentionally the first time you use this release. The app confirms direct file editing before opening it and again on startup. This mode does **not** edit `TEW9Save.mdb` or update existing save games.

**External modification guard:** the application captures the active MDB's size and last-write timestamp on opening and rejects Save Changes or generated title-reign replacement if those file attributes change before a write. Refresh Database discards pending unsaved edits after confirmation, reconnects, and rereads workers and other entities. Metadata checks reduce accidental stale edits but cannot guarantee conflict prevention against simultaneous writers; do not have both editors open for editing.

**Create Backup** remains separate and manual. It closes the connection momentarily, copies the saved active MDB to the configured Backup Folder (or a sibling `Backups` folder), then reopens the connection. It does not include unsaved fields. **Export Copy As** similarly creates a new file without switching the active database and without overwriting existing files. A manual backup is recommended but optional before testing unverified TEW data modifications, especially title lineage generation.

The password is requested for each session unless encrypted password remembering is enabled. When enabled, the password is encrypted with Windows-user DPAPI and stored outside settings.json. No credentials, database files, or game assets should be committed to the repository.

## Runtime requirements

Microsoft Access Database Engine/ACE OLE DB compatible with win-x64 is required. The app tries ACE 16 and ACE 12, with several connection string variants. It cannot install an Access driver on its own. If a particular database fails to connect, confirm the database file and provider's architecture and configuration.

## Validation caveats

A write succeeding does not establish in-game compatibility. Always open the resulting working copy as a TEW IX scenario in a separate test environment, run TEW's Data Check, and create a **new game** when testing scenario edits. Existing saves do not incorporate edits from scenario MDBs. Application validation currently checks database value types and update row counts, not the many TEW-specific rules, enumerations and foreign keys. It is easy to create data TEW rejects.

GitHub releases are currently **unsigned**. The installer updater compares SHA-256 checksums with the matching GitHub Release metadata and then runs Inno Setup in quiet mode after the editor closes. A future production release should use Windows code signing.
